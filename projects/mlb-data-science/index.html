Case study

MLB Data Science Prediction System

Python · PySpark · Pandas · Random Forest Classifier · REST APIs · Google Colab

What it does

A full data pipeline that pulls real MLB game data from the BallDontLie REST API, cleans and transforms it with PySpark, engineers performance features per team, and trains a Random Forest classifier to predict game outcomes and flag high-volatility matchups. The pipeline runs end to end: API → ingestion → cleaning → feature engineering → model training → prediction → CSV reports that a dashboard tool like Power BI can consume directly.

The features

Each team gets rolling performance indicators going into a game: offensive performance, defensive performance, average hits per game, and average defensive errors, computed separately for home and away teams from their historical game logs.

What the model actually found

Here's the part I want to be upfront about rather than gloss over: the two most "important" features to the Random Forest model are the home and away team IDs themselves (28.8% and 21.3% of total importance) — not the engineered performance stats I actually built the pipeline to produce. In plain terms, the model leaned heavily on which teams are playing rather than how they've been performing. That's a real limitation: it suggests the model is partly memorizing team identity (some teams simply win more often in this dataset) instead of learning a generalizable signal from the performance features. A more rigorous next version would drop or heavily regularize the raw team ID features and force the model to rely on the engineered stats.

Flagging risk, not just predicting outcomes

Beyond a straight win/loss prediction, the pipeline classifies each historical game by risk: of 17 games analyzed, 8 were flagged "Alta Volatilidad (Evitar)" — games where the model's predicted probabilities were close to a coin flip — and 9 were flagged as a clear mathematical favorite. Separately, 4 of the 17 were tagged"ROMPE-QUINIELAS" (upset alert): games where the model's favorite lost. That's the kind of output that's actually useful for a betting-adjacent or fantasy-sports use case — not just "who wins" but "how much should you trust this prediction."

Stack & why

PySpark for the ETL because the historical game-log data needed real transformation work (parsing nested play-by-play fields, computing rolling averages) at a scale where plain pandas gets slow. Random Forest over a simpler model because the features are a mix of scales and I wanted a model that handles that without heavy manual scaling, and because feature importance output is exactly what let me catch the team-ID issue above — a black-box model would have hidden it.
